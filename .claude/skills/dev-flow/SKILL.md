# dev-flow

danmalgi_api 의 개발을 세 단계로 진행한다. **단계를 건너뛰지 않는다.**

요구사항이 한 줄짜리 자명한 수정(오타, 상수값 하나)이면 이 흐름은 과하다.
그럴 땐 그냥 고치고 `scripts/verify.sh --changed` 만 돌려라.

---

## 1단계 — PLAN

`planner` 에이전트를 부른다. 직접 코드를 뒤지기 전에 이것부터 한다.

```
Agent(subagent_type: "planner", prompt: "<요구사항 원문> + 이번 대화에서 나온 제약")
```

요구사항을 요약하지 말고 **원문 그대로** 넘겨라. 사용자가 언급한 파일명, 에러
메시지, 제약은 전부 포함한다. planner 는 코드를 수정하지 않는다.

planner 가 돌아오면 결과를 **간결하게** 정리해 사용자에게 보여준다.

- 수정할 파일 목록 (경로)
- 단계별로 무엇을 할지
- 추가할 테스트 클래스명
- planner 가 짚은 위험이나 불확실한 점

그리고 **거기서 멈춘다.** `AskUserQuestion` 으로 승인을 받는다.
승인 없이 2단계로 넘어가지 마라. 계획이 틀렸을 때 코드가 이미 바뀌어 있는
상황을 막으려는 것이다.

사용자가 계획을 고치라고 하면 그 피드백을 담아 planner 를 다시 부른다.

---

## 2단계 — WORK

승인된 계획대로 **네가 직접** 구현한다. 이 단계는 에이전트에 넘기지 않는다.

지켜야 할 것:

- **레이어 순서**: validator → service → mapper → gRPC 핸들러.
  요청 흐름과 같은 방향이라 중간에 뭐가 빠졌는지 알아채기 쉽다.
- **테스트를 같이 쓴다.** 메서드 하나당 테스트 클래스 하나, 소스와 같은 패키지,
  이름은 `<Class><MethodPascal>Test`. (mapper/validator 는 접두어 없는
  `<MethodPascal>Test` 도 쓴다) 테스트를 3단계로 미루지 마라.
- **손대면 안 되는 것**: `src/main/proto/**` 는 git 서브모듈이라 이 리포에서
  수정할 수 없다. `build/generated/**` 는 생성 코드다. proto 스키마 변경이
  필요하면 구현을 멈추고 사용자에게 알려라.
- 계획에 없던 것을 발견하면 임의로 범위를 넓히지 말고 사용자에게 먼저 말한다.

---

## 3단계 — REVIEW

`reviewer` 에이전트를 부른다.

```
Agent(subagent_type: "reviewer", prompt: "이번 변경을 검증해라. scripts/verify.sh --changed 를 기준으로,
변경한 파일: <목록>. 요구사항: <한 줄 요약>")
```

reviewer 는 코드를 수정하지 않는다. 돌리고 보고만 한다.

### 통과하면

결과를 요약해 보고한다. 무엇을 바꿨고, 어떤 검증을 통과했는지.
SKIP 된 단계가 있으면 **SKIP 이라고 말한다.** 통과로 포장하지 마라.

### 실패하면 — 최대 2회까지 고치고 재검증

1. reviewer 가 보고한 원인을 읽는다. 로그를 다시 뒤지지 말고 보고를 쓴다.
2. 고친다. **원인을 고치는 것이지 테스트를 느슨하게 만드는 게 아니다.**
   테스트 단언을 약화시키거나 검사를 끄는 방향은 금지다.
3. reviewer 를 다시 부른다. (재시도 1회 소진)

2회 재시도로도 통과하지 못하면 **거기서 멈춘다.** 계속 시도하지 말고 보고한다.

- 무엇이 아직 실패하는지
- 두 번의 시도에서 무엇을 바꿨고 왜 안 됐는지
- 네가 의심하는 원인과, 확인하려면 뭐가 필요한지

같은 수정을 반복하고 있다면 2회를 채우기 전에 멈춰라. 접근이 틀린 것이다.

## 보고 형식

```
계획   승인받은 계획 한 줄 요약
변경   파일별로 무엇을 했는지 (경로:줄번호)
검증   reviewer 결과 — 단계별 PASS/FAIL/WARN/SKIP
남은 것 손대지 않은 것, 확인 못 한 것
```

돌리지 않은 검사를 돌렸다고 쓰지 마라. 불확실하면 불확실하다고 써라.
